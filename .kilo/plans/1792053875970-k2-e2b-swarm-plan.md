# K2 Distributed Adapter 1 — e2b Swarm (plan)

Status: DRAFT — awaiting approval on the two forks marked ⚑ before implementation.

## Goal

`k2 swarm --provider e2b --nodes N --target <url>` fans a single campaign out
across N e2b Firecracker sandboxes. One **coordinator** (the local k2 process)
runs the closed loop over *aggregated* telemetry; every **worker node** is a
dumb executor that schedules its share of the intents and streams snapshots
home.

## Scope decision context

- Single-node K2 comfortably emits 5-20k RPS (boringssl handshake ~0.5-1ms CPU,
  keep-alive pooling). **Distribution is not primarily about capacity.**
- Real reasons to distribute: (1) aggregate capacity beyond one box's CPU/FD/
  egress budget, (2) multi-region vantage (latency measured from where users
  are), (3) egress diversity — where e2b is weakest (sandboxes NAT through
  host IP pools; per-sandbox source-IP diversity is NOT guaranteed).
- Positioning: e2b adapter = capacity + vantage. Per-IP-diversity adapters
  (SSH-to-VPS, residential pools, WireGuard mesh) come later; the control-plane
  seam is provider-agnostic by design.
- 20-sandbox quota ⇒ ~20-60k RPS aggregate (each sandbox runs its own full
  worker pool, Little's-law-scaled). Plenty for app-hardening campaigns.

## Architecture

```
 Local k2 (coordinator)                     e2b sandboxes × N
 ┌────────────────────────────┐             ┌──────────────────────┐
 │ CLI + controller + merged  │  rate cmds  │ k2 --node-mode       │
 │ telemetry (sum + Agg merge)│◄────────────┤  scheduler@rate/N    │
 │ + final merged report      │──snapshots─►│  engines + workers   │
 │ + web/TUI surfaces         │  (HTTP)     │  (no controller/UI)  │
 └────────────────────────────┘             └──────────────────────┘
        ▲  e2b REST API: create/kill sandboxes, upload binary, exec
```

- **Node mode** (`k2 --node-mode <coordinator-url>`): scheduler + engines +
  workers only. Streams `Snapshot` JSON (500ms cadence, batched, gzipped) to
  the coordinator; applies rate commands. Honors existing seams:
  `TelemetrySink` trait gains an HTTP impl; `ControlPlane` gains HTTP-poll impl.
- **Coordinator merge**: counts/statuses/errors sum; latency merges via the
  existing `Agg::add_bucket` (bucket-compatible histograms — the win from the
  hand-rolled HDR). Controller consumes the merged snapshot: one knee-hunt
  governing the whole fleet.
- **e2b transport**: wreq (already in tree) against the e2b REST API with
  `E2B_API_KEY`. Cold start: create N sandboxes in parallel, upload the k2
  release binary (~10-15MB, one upload reused via sandbox snapshot/template),
  exec `./k2 --node-mode ...`.
- **Lifecycle**: coordinator owns sandbox TTL (campaign duration + 60s grace),
  kills on completion/cancel, drains gracefully like local runs.

## New CLI surface

```
k2 swarm --provider e2b --nodes 8 [--region ...] [regular campaign flags]
# env: E2B_API_KEY
```

## Milestones

1. **D1 seams**: `TelemetrySink`/`ControlPlane` traits extracted; local run
   refactored onto them (no behavior change). Node-mode flag (no-op transport).
2. **D2 e2b provider**: sandbox create/upload/exec/kill via REST; parallel
   boot; error taxonomy (quota, auth, region).
3. **D3 merge + loop**: coordinator aggregation (Agg merge), rate broadcast,
   merged final report (per-node + total tables).
4. **D4 tests**: fake-provider integration (local HTTP nodes instead of e2b),
   merge math unit tests, quota/auth failure paths. e2b live test stays manual
   (needs API key) behind `E2B_API_KEY` presence check.

## ⚑ Fork 1 — worker-node telemetry transport

- **A. HTTP POST to coordinator** (recommended): coordinator's axum server
  gains `/api/ingest`; nodes push snapshots. Zero extra infra, works through
  e2b's public hostnames, 500ms × N nodes = trivial load.
- B. Coordinator dials nodes over e2b's WebSocket exec streams — more moving
  parts, no real benefit.

## ⚑ Fork 2 — node binary delivery

- **A. Upload-once + snapshot template** (recommended): first run uploads the
  release binary and bakes it into a private e2b template; later runs boot in
  ~1-2s with zero transfer. Requires one-time `e2b template build` step.
- B. Upload the binary on every campaign (simpler, +10-30s per run, no
  template management).
- Recommendation: start with B, add A as `k2 swarm provision` when it hurts.

## Out of scope (later adapters)

SSH-to-VPS (real IP diversity), residential proxy pools, WireGuard mesh,
Nomad/K8s/Fly provisioning.
